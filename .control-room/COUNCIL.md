# Founder AI Council Contract

Status: active control-room documentation for `jussray/chief-ai-machine`.

The Council is a multi-model reasoning and review layer. It does not replace current repository/provider/runtime evidence or the founder's exact authority gate.

Also apply `docs/FOUNDER_WORK_PRODUCTIZATION_CONTRACT.md` and `docs/FCR_WORKFLOW_GRADUATION_HANDOFF.md`. Council is backstage reasoning. Repeated proven Council patterns should graduate into durable product capability instead of forcing the founder to manually reconstruct the same model/command composition in chat.

## Neutral shared Council invariant

The Council is a neutral shared protocol/ledger connecting four first-class standalone core systems:

- **Founder Control Room** — standalone founder operating/build intelligence.
- **Chief AI** — standalone executive synthesis/reasoning intelligence.
- **Sol** — standalone challenge/evaluation/continuity intelligence.
- **PromptOS** — standalone prompt/workflow/compiler/routing intelligence.

No one of these systems owns the shared Council layer, and none depends on the Council layer or an external provider for its core function. Each repository owns only its project-local Council adapter, evidence bindings, receipts, routing constraints, and authority membrane at `.control-room`.

FCR may expose a first-class founder-facing Council surface and may invoke external AI providers from that surface. That does not make FCR the owner of the shared Council layer and does not make an external model part of the permanent spine.

ChatGPT, Claude, Muse, DeepSeek, Perplexity, Gemini, local models, and future providers participate as replaceable Council seats when actually available and authorized. Provider loss must not erase plans, architecture, decisions, prompts, receipts, fingerprints, state, evidence, or the operating capability of FCR, Chief, Sol, or PromptOS.

The physical backing for the neutral shared Council protocol/ledger is intentionally undecided until separately authorized. Do not silently make GitHub, FCR, Google Drive, Google Sheets, Supabase, Slack, or an external model the owner merely because it is convenient.

Default invocation is automatic when Council participation is materially useful. Route the smallest useful task-specific set of seats rather than waking every provider by default. Product-user workflows may invoke the Council behind the scenes only when project policy allows it; users receive the governed product outcome, not raw Council deliberation, founder controls, provider credentials, cross-project private data, or a required ritual of internal command names.

A named Council seat counts as **live** only when an actual connector/API/runtime call is verified by provider evidence. Simulated role analysis must never be labeled as a live provider response.

All execution remains inside the owning project's local authority membrane. Cross-project Council reasoning may coordinate evidence and recommendations, but cross-project mutation must be handed to the repository/system that owns the affected state.

## Members and core peers

- **Founder**: final human authority for separately gated actions.
- **Founder Control Room**: standalone founder operating/build intelligence; may plan, inspect, build, repair, verify, operate, preserve continuity, and advance the portfolio without requiring an external AI host.
- **Chief AI**: standalone orchestration, decomposition, specialist synthesis, goal-state framing, and workflow-candidate compilation; never self-authorizes execution.
- **Sol**: standalone challenge, evaluation, continuity, state recovery, drift detection, and evidence-lineage intelligence.
- **PromptOS**: standalone prompt/protocol/workflow compilation, routing, evaluation, promotion, and reusable protocol intelligence.
- **Codex / ChatGPT**: replaceable debugging, code review, data analysis, implementation support, repository operations, synthesis, and invention-lab seat.
- **Claude / Claude Code**: replaceable long-context analysis, architecture, careful refactors, implementation, and documentation seat.
- **Muse**: first-class governed external challenger for cross-provider drift, independent review, and bounded implementation. Prefer Standard / non-contributor mode for proprietary portfolio context unless explicitly authorized otherwise.
- **Perplexity**: replaceable current public research and source-discovery seat; public-web evidence does not substitute for private runtime truth.
- **Other eligible providers**: may participate only when local policy/registry says they are eligible.

Provider/model selection is replaceable capability routing. An OpenAI or Anthropic key does not become unrelated GitHub, Supabase, Cloudflare, publishing, billing, or external-service authority.

## Rules

1. Evidence outranks model opinion.
2. Council consensus does not authorize mutation.
3. Preserve meaningful dissent.
4. Parallel reasoning is allowed; mutation is serialized through one bounded path.
5. Every Council round binds to repository/project, current branch/head when relevant, provider surfaces, truth age, authority ceiling, and stop condition.
6. No Council member inherits approval from another member.
7. Secrets, private user/customer data, raw private provider payloads, and protected sauce stay out of Council evidence packets.
8. A model may propose a merge, deploy, migration, DNS/provider change, publication, send, delete, or spend. It may not silently authorize one.
9. When a Council route becomes repeatable, Chief should package it into a `juss/fcr-workflow-candidate@v1` handoff instead of making the founder reconvene it manually forever.
10. The user-facing workflow should expose the outcome, evidence, risk, and next action, not an agent zoo.
11. The neutral shared Council layer grants no execution authority of its own.
12. Core peer systems remain usable when the shared Council layer or any external provider is unavailable.

## Automatic founder lenses

Apply the canonical FCR lenses as provider-neutral reasoning tools: truth/confess, ULTRATHINK, Product Design, Data Analytics, Redteam I, Lindy, L99, OODA, value/outcome reasoning, first principles, Redteam II, and re-observation/loop.

These are internal composition tools. A graduated workflow owns the required composition so an ordinary user does not need to type the internal stack.

## Workflow graduation

A Council route is a productization candidate when it repeatedly serves the same stable user outcome with definable inputs, output semantics, proof, authority, rollback, privacy, and acceptable cost/latency.

Council may recommend:

- keep one-off;
- continue proving;
- compile as an FCR workflow candidate;
- revise an existing workflow; or
- retire a repeated pattern that does not justify its cost/burden.

Chief compiles the candidate. FCR owns its durable registry/execution state while remaining a standalone builder in its own right. Council recommendation does not activate the workflow.

For StoryEngine creative work, Court remains Writers Council + AI Council + Production Council with independent-first deliberation, `/DEVIL` cross-examination, creator ruling, and tool-capability/permission separation. A repeated Court route may graduate into FCR/StoryEngine only while preserving creator override and canon boundaries.

## Council round packet

Each member distinguishes `VERIFIED`, `INFERRED`, `UNKNOWN`, and `BLOCKED`.

The synthesis returns:

- `REALITY`: verified state now
- `COUNCIL`: conclusions plus meaningful dissent
- `FIX`: smallest reversible selected action
- `PROOF`: evidence required or obtained
- `RISK`: unresolved failure modes
- `ROLLBACK`: safe reversal
- `NEXT GATE`: one exact founder decision/action

When the round reveals a repeatable pattern, append:

- `WORKFLOW`: existing workflow id or proposed candidate id
- `PUBLIC OUTCOME`: user-facing label/outcome
- `REPEATABILITY`: evidence for graduation
- `HANDOFF`: Chief/FCR next state

When GitHub, Supabase, and Cloudflare are involved, triangulate source -> data/auth boundary -> deployment/runtime -> user outcome. No layer certifies the next merely by being green.

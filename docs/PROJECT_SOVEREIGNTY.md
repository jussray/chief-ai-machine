# Project Sovereignty Contract

Chief must remain a provider-independent founder-intelligence and coordination system whose core reasoning contracts, evidence semantics, and recovery paths survive loss of any single model, provider, connector, runtime, vendor, or sibling project.

## Invariants

- **Human authority comes first.** Authorized humans are the root of consequential authority. Models, agents, providers, workflows, evidence, learned knowledge, fingerprints, proof cookies, and automations may inform or constrain a proposal but may not manufacture, renew, widen, or replay authority.
- Human authority does not rewrite reality. Approval can authorize an action; only evidence can support a truthful execution or outcome claim.
- Chief may reason, compose, inspect, recommend, simulate, and prepare bounded proposals. It does not gain execution authority merely because it knows what should happen.
- Chief-owned contracts define canonical inputs, outputs, errors, authority, state, evidence, and completion semantics.
- Founder Control Room remains the founder-facing authority/evidence/outcome control plane when Chief is operated through FCR. Chief remains a sovereign reasoning subsystem, never a separate founder OS, and Chief and FCR must each preserve enough identity, contracts, and safe degraded behavior to survive temporary loss of the other.
- External models, SDKs, APIs, MCPs, plugins, connectors, runtimes, and vendors are replaceable capabilities, not Chief's identity.
- Critical dependencies are classified `REPLACEABLE`, `DEGRADED_FALLBACK`, `HARD_DEPENDENCY`, or `UNKNOWN`.
- A critical capability needs an alternate adapter, local/open implementation, deterministic fallback, export/manual recovery path, or honest safe degraded mode unless a documented hard dependency is explicitly accepted.
- Critical data keeps Chief-owned semantics and a migration/export path.
- Provider/model loss may reduce quality or capability but must not silently erase mission state, authority boundaries, evidence meaning, or recovery instructions.
- Provider swaps must not broaden tool permissions, replay stale approvals, duplicate mutations, or weaken evidence requirements.
- Provider-specific results map into Chief-owned/project-owned receipts and then into FCR's shared proof model when FCR is the control plane; provider acceptance is not founder-goal outcome proof.

## World as experience and knowledge

Legitimate real-world interaction may become evidence-bearing experience: founder reports, provider/runtime results, repository history, experiments, analytics, documents, operational failures, tool observations, and verified outcomes.

```text
World → observation → provenance → evidence classification → experience receipt → knowledge candidate → contradiction / red-team check → context + confidence + freshness → working knowledge → proposal → authorized action when applicable → outcome evidence → new experience
```

Experience is not automatically truth. One observation is not automatically a durable rule. Working knowledge must remain provenance-backed, scoped, challengeable, freshness-aware, and supersedable.

## Chief-specific boundary

Knowledge, reasoning quality, confidence, model consensus, tool availability, or prior success never create authority. Chief must keep `knowledge`, `experience`, `authority`, `evidence`, `execution`, and `outcome` as separate planes. A stronger model or fallback provider may improve reasoning but may not raise the authority ceiling.

## Mandatory audit questions

> If FCR, the current model provider, MCP layer, or another named dependency disappeared now, what stops, what survives, what degrades safely, what is the recovery path, and what evidence proves the answer?

> What experience is Chief learning from, what would falsify the current conclusion, and which authorized human or control-plane gate actually permits the next consequential action?

Architecture docs are not failover or learning proof. Verify contract, provider adapter, deterministic/degraded path, focused test, runtime, data exit, authority, and real-path evidence separately.

Use the canonical founder challenge stack: Reality → ULTRATHINK → Red Team 1 → Lindy → L99 → Red Team 2 → OODA → Proof → Rollback / Next Gate. OODA selects the smallest reversible implementation that existing authority permits; proof must remain bound to the final exact state.

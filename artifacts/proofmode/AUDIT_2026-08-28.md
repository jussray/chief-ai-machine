# ProofMode Main Audit — 2026-08-28

Audited base: `2fd4fda0cab12e52ab5096e723884d98bcfe7d10` (`main`)

Continuation review: `2026-08-29`

## Confirmed findings addressed in this candidate

1. `pull_request_target` workflow runs could be misattributed as exact-head test proof because GitHub reports base-branch context for that event. ProofMode now preserves workflow event/head provenance and excludes `pull_request_target` from exact-head testing support.
2. Test files could inflate implementation-source counts because any recognized code extension was counted. Test artifacts are now excluded from implementation source.
3. The served MCP tool lacked explicit read-only authority annotations. `audit_repository` now declares read-only, non-destructive, idempotent, open-world semantics.
4. The legacy MCP endpoint rejected GET with 405 while advertising `Allow: POST, GET`. It now advertises only `POST`.
5. The nested ProofMode package used Node's built-in test runner for Vitest tests. It now delegates to a named root `verify:proofmode` contract.
6. The live ProofMode PR workflow did not trigger for classifier/provider changes. It now covers `plugins/proofmode/**`, package manifests, and the served Worker surface, and runs the named contract before Playwright.
7. The production ProofMode workflow used floating GitHub Action tags while the preview workflow already used repository-approved commit pins. Production now uses the same pins and runs the named ProofMode contract.
8. ProofMode documentation described a core-only branch state that no longer matched `main`. README and product contract now describe the served MCP boundary without claiming runtime verification.
9. The GitHub evidence loader had no focused provider-boundary tests. The focused provider suites now cover workflow provenance, anonymous-only evidence collection, private/ambiguous repository refusal, public-to-private transition failure, permission refusal, and rate-limit classification.
10. The optional server-held GitHub credential was originally attached to repository evidence requests. That could expand v0.1 into data the anonymous public caller was not authorized to see. ProofMode v0.1 now performs all GitHub repository evidence reads without credentials, and the MCP Worker does not forward `PROOFMODE_GITHUB_TOKEN` into repository audits even if that environment variable exists.
11. Pinning the production ProofMode workflow made three temporary `@v4` operational-authority waivers obsolete. The authority verifier correctly failed closed on those stale waivers; this candidate removes only those no-longer-applicable waiver entries while preserving the immutable action pins.
12. Existing provider tests previously encoded authenticated follow-up behavior. They now enforce anonymous-only public evidence collection, and the named `verify:proofmode` contract includes both provider regression suites so this boundary cannot silently drift outside the focused verification command.
13. Exact-head Cloudflare builds succeeded, but both ProofMode and the broader Chief immutable-preview witnesses were redirected to the Cloudflare Access login even while a service-token pair was present in the workflow environment. This is provider-side authorization evidence: the configured token is not currently accepted by a matching Service Auth policy, is invalid/disabled/expired, or the Access application policy does not include it. The ProofMode workflow now reports this state accurately instead of incorrectly saying only that credentials need to be configured.
14. A successful workflow could previously satisfy exact-head testing when its `headSha` provenance was missing. Exact-head workflow evidence now fails closed unless a non-empty workflow head SHA exactly matches the audited commit.
15. Repository metadata with ambiguous visibility could previously pass the public-repository boundary when it did not explicitly identify the repository as private or internal. ProofMode now requires positive public evidence: `private === false` and `visibility === "public"` before repository evidence is classified.
16. The MCP runtime advertised `additionalProperties: false` and strict acknowledgement receipt IDs but did not enforce those constraints before GitHub access. Runtime validation now rejects unsupported arguments, caller-supplied credential-like fields, empty refs, malformed receipt IDs, duplicate acknowledgements, and oversized acknowledgement lists before any provider request occurs.
17. Cloudflare Access credentials were previously present at workflow scope, causing setup, dependency-install, and unrelated verification steps to inherit them. The ProofMode and Chief immutable-preview workflows now scope Access secrets only to the exact-head readback and live Playwright steps. Automatic preview resolution also requires the official `cloudflare-workers-and-pages` GitHub App plus an approved immutable `chief-ai` `workers.dev` version host before any Access credential can be sent.
18. Generic successful workflows such as `Lint`, `Build`, `Quality Gate`, `Check`, `CI`, or generic verification could previously satisfy the `Tested` layer merely because test files existed in the repository. v0.1 now requires an explicitly test-oriented successful workflow name with exact matching head provenance. Generic green workflow evidence remains partial until richer job-level Actions evidence can prove tests actually ran.
19. The live ProofMode Playwright witness now binds the emitted `juss-proof/v1` receipt to the exact audited repository and SHA, and separately proves that the `verified` layer remains `not_proven`/`unknown` rather than treating repository evidence as a runtime witness.
20. Unexpected internal exceptions could previously expose arbitrary exception messages through MCP tool results. Known bounded GitHub provider failures retain their safe machine-readable error codes/messages, while unknown internal failures are now returned as `audit_failed` with a generic redacted message.
21. Review identified a time-of-check/time-of-use privacy gap in the intermediate public-first/authenticated-follow-up design: a repository could become private after the public metadata check while a privileged server token continued to read private evidence. The final v0.1 design removes the privileged follow-up path entirely. Every repository evidence request is anonymous, so a visibility transition causes subsequent GitHub reads to fail closed instead of crossing the public-only boundary.

## Evidence boundaries preserved

- Repository evidence does not become runtime verification.
- GitHub repository evidence collection is anonymous-only in v0.1; no server credential may expand the public evidence boundary.
- Deployment configuration and provider deployment records remain partial evidence.
- A production workflow `startup_failure` with zero jobs is infrastructure/startup evidence, not a ProofMode test failure.
- A successful Cloudflare build is not a live runtime witness when Cloudflare Access prevents the exact preview from being read back.
- Missing or ambiguous provenance fails closed rather than being interpreted as proof.
- Generic green CI does not prove tests ran unless the available evidence explicitly demonstrates a test-oriented workflow for the exact audited head.
- The served MCP transport remains explicitly legacy-2025. The 2026 MCP revision is a different stateless transport contract and is not claimed by this candidate.
- A future SDK-v2 transport migration requires its own dependency, bundle, preview, and runtime proof.
- Existing repository dependency warnings (`glob@10.5.0` deprecation and the npm audit findings already present on audited `main`) are retained as separate dependency debt; this ProofMode correctness candidate does not perform an unrelated lockfile upgrade.

## Unresolved contract semantic — not changed in this candidate

The current `juss-proof/v1` ProofMode receipt writes `exactTarget.branch` from the generic audit `ref`. The tool input explicitly allows a branch, tag, or commit SHA, so a SHA-addressed audit can currently serialize that SHA into a field named `branch`. The live witness no longer asserts that this field proves branch semantics; it binds authority to `exactTarget.repository` plus `exactTarget.sha` instead. The receipt schema is not changed in this candidate because no authoritative shared contract definition was found that would justify an incompatible field change. Resolve this through the canonical federated-proof contract before changing the schema.

## Current external blocker

Cloudflare must accept the CI service token for the immutable Worker preview before merge promotion. The Access application protecting the preview must have a matching `Service Auth` policy that includes the configured service token, and the token must be enabled and unexpired. This is an external provider configuration gate; no repository secret values are recorded here.

The Cloudflare account connector/plugin is not exposed in the current execution surface, so this audit does not claim to have changed Zero Trust policy or service-token configuration.

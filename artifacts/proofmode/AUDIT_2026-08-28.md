# ProofMode Main Audit — 2026-08-28

Audited base: `2fd4fda0cab12e52ab5096e723884d98bcfe7d10` (`main`)

## Confirmed findings addressed in this candidate

1. `pull_request_target` workflow runs could be misattributed as exact-head test proof because GitHub reports base-branch context for that event. ProofMode now preserves workflow event/head provenance and excludes `pull_request_target` from exact-head testing support.
2. Test files could inflate implementation-source counts because any recognized code extension was counted. Test artifacts are now excluded from implementation source.
3. The served MCP tool lacked explicit read-only authority annotations. `audit_repository` now declares read-only, non-destructive, idempotent, open-world semantics.
4. The legacy MCP endpoint rejected GET with 405 while advertising `Allow: POST, GET`. It now advertises only `POST`.
5. The nested ProofMode package used Node's built-in test runner for Vitest tests. It now delegates to a named root `verify:proofmode` contract.
6. The live ProofMode PR workflow did not trigger for classifier/provider changes. It now covers `plugins/proofmode/**`, package manifests, and the served Worker surface, and runs the named contract before Playwright.
7. The production ProofMode workflow used floating GitHub Action tags while the preview workflow already used repository-approved commit pins. Production now uses the same pins and runs the named ProofMode contract.
8. ProofMode documentation described a core-only branch state that no longer matched `main`. README and product contract now describe the served MCP boundary without claiming runtime verification.
9. The GitHub evidence loader had no focused provider-boundary tests. New tests cover workflow provenance, public-before-auth behavior, private-repository refusal, and rate-limit classification.
10. The optional server-held GitHub credential was attached to the initial repository metadata request. A credential with private access could therefore reveal private repository metadata before v0.1 rejected the repo. The loader now establishes public visibility without credentials first and only then permits the server-held token on subsequent public evidence reads.
11. Pinning the production ProofMode workflow made three temporary `@v4` operational-authority waivers obsolete. The authority verifier correctly failed closed on those stale waivers; this candidate removes only those no-longer-applicable waiver entries while preserving the immutable action pins.

## Evidence boundaries preserved

- Repository evidence does not become runtime verification.
- Deployment configuration and provider deployment records remain partial evidence.
- A production workflow `startup_failure` with zero jobs is infrastructure/startup evidence, not a ProofMode test failure.
- The served MCP transport remains explicitly legacy-2025. The 2026 MCP revision is a different stateless transport contract and is not claimed by this candidate.
- A future SDK-v2 transport migration requires its own dependency, bundle, preview, and runtime proof.
- Existing repository dependency warnings (`glob@10.5.0` deprecation and the npm audit findings already present on audited `main`) are retained as separate dependency debt; this ProofMode correctness candidate does not perform an unrelated lockfile upgrade.

## Candidate verification gates

- `npm run verify:proofmode`
- root quality/type/lint/test gates required by repository policy
- operational-authority verifier with zero stale/mutable action waiver violations
- immutable Cloudflare commit preview resolving the exact PR head
- live `/version` exact-head readback
- live `/mcp` initialize, tools/list, read-only annotations, method boundary, and exact-repository audit via Playwright
- merge-intent and independent repository/provider gates

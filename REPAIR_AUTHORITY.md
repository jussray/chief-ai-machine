# Chief AI Repair Authority

Chief remains the reasoning/composition layer. More intelligence never means more authority. This contract defines the repairs Chief and its trusted operators may perform without converting recommendations, fingerprints, proof cookies, or model output into execution permission.

## Standing necessary-fix rule

When current evidence proves a defect inside Chief's own repository or governance surface, a trusted acting operator may implement the smallest focused reversible repair, add/update the narrowest useful test, refresh documentation, and rerun the relevant exact-head proof without waiting for a second approval that adds no new authority information.

Every repair must bind to the canonical repository, current base/head, affected surface, failure fingerprint, evidence-only proof cookies, rollback, and post-repair verification. Head/base movement expires predecessor proof.

## Chief-owned repair authority

Chief/trusted source operators may:

- repair Chief source, tests, CI/workflow contracts, schemas owned by this repository, and governance documentation;
- repair stale or contradictory Chief/FCR pair metadata after independently re-reading the current peer evidence;
- rerun failed GitHub jobs when rerun is the correct diagnostic action;
- update existing PR/issue receipts with exact current evidence;
- restore browser-local/UI behavior owned by Chief and verify it with real Playwright when the rendered path changes;
- merge only when the current repository merge policy independently authorizes the exact candidate.

Chief may generate a proposal, plan, recommendation, capability intent, or repair candidate for another system. That artifact remains non-authorizing until the owning execution plane validates and accepts it.

## Witness-triggered repairs

- GitHub/local tests may trigger source/test/CI repair.
- Playwright may trigger UI/browser repair and must verify rendered-path fixes.
- Cloudflare provider evidence may trigger a provider repair request, but candidate/source code may not consume protected admin credentials merely because it observed a failure.
- Founder Control Room may execute the bounded external/provider mutation when its current trusted authority membrane authorizes that exact action.
- Linear/Asana may repair tracker state only.
- Notion/Drive/docs may repair documentation state only.
- Slack/internal communication may repair incident/status records only.

## Provider authority boundary

Chief does not gain standing provider-admin authority from this file. A Cloudflare or other provider mutation is permitted only through an already-trusted execution carrier that independently verifies:

- exact provider account/project/application identity;
- current repository/release identity;
- provider subject/credential class;
- before state and rollback target;
- bounded reversible desired state;
- post-write provider readback;
- browser/runtime proof when user-observable.

Candidate-authored workflow code must not bootstrap itself into protected provider secrets or admin environments.

## Hard gates

Keep explicit founder authority for:

- scope or authority expansion;
- new spending/billing;
- external publication or communication outside an already-approved automation;
- destructive/irreversible changes;
- secret creation/exposure/rotation/deletion;
- account/ownership transfer;
- auth/identity/access-policy changes that materially widen who can act or see data.

## Truth rule

A witness can trigger a repair without owning the repair authority. Trackers and messages are evidence about work; they are not execution principals. Cloudflare proves provider/runtime state, not source correctness. GitHub proves repository state, not production behavior. Playwright proves observable behavior, not merge/deploy permission.

For consequential repairs report REALITY, WITNESSES, FIX, PROOF, RISK, ROLLBACK, NEXT GATE.
